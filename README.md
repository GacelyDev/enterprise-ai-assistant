# Enterprise RAG Assistant & Analytics Engine

> A modular RAG prototype for enterprise financial research that combines a console-based assistant, browser-based data ingestion, local vector search, and session analytics. It is built with LangChain orchestration, ChromaDB vector storage, and a locally hosted Ollama `phi3` model to preserve data privacy and support self-contained evaluation.

## 1. Prerequisites

Before starting, ensure you have the following installed on your local machine:
* **Docker** (version 20.10+)
* **Docker Compose** (version 2.0+)
* **Git**
* Adequate hardware resources (at least 8GB of RAM allocated to Docker to smoothly run local embedding models and `phi3`).

---

## 2. Environment Configuration

1. Clone the repository and navigate into the project root directory:
   ```bash
   git clone <repository-url>
   cd enterprise-ai-assistant
   ```

2. Create a .env file in the root directory based on your environment needs. Below is an example configuration:
    ```sh
    # ==========================================
    # WEB SCRAPING CONFIGURATION
    # ==========================================
    SCRAPE_DATA=True
    TARGET_URL=https://www.bancoagrario.gov.co/
    SCRAPE_MAX_PAGES=20
    MIN_WORDS=10
    CHUNK_SIZE=1024
    CHUNK_OVERLAP=128

    # ==========================================
    # VECTOR DATABASE CONFIGURATION
    # ==========================================
    VECTOR_DB_HOST=vector_db
    VECTOR_DB_PORT=8000
    ANONYMIZED_TELEMETRY=False
    EMBEDDING_MODEL=all-MiniLM-L6-v2

    # ==========================================
    # RAG ASSISTANT CONFIGURATION
    # ==========================================
    MAX_HISTORY_MESSAGES=4
    CHROMA_HOST=vector_db
    OLLAMA_BASE_URL=http://ollama_server:11434
    PROMPT_VERSION=v1
    SESSIONS_DIR=/app/data/sessions
    ```

## 3. Step-by-Step Execution Guide
To ensure smooth initialization of the vector database, the local LLM server, and data pipelines, the initial run must be performed sequentially.

1. Start Infrastructure Services: Bring up the vector database and the local Ollama LLM server in the background:
    ```bash
    docker compose up -d vector_db ollama_server
    ```
2. Download the LLM Model: Because the Ollama container starts empty, you must manually pull the required language model before executing queries:
    ```bash
    docker exec -it ollama_llm ollama pull phi3
    ```
3. Run the Data Ingestor Pipeline: Execute the scraping and data ingestion pipeline to populate the vector database with financial documents:
    ```bash
    docker compose run --rm data_ingestor
    ```
4. Launch the Interactive RAG Console: Once data is ingested and the model is downloaded, start the interactive console assistant:
    ```bash
    docker compose run --rm rag_console
    ```

### Subsequent Starts
After the database has been created and the model has been downloaded, a second execution can start the service stack directly without rerunning ingestion.

```bash
docker compose up -d
```

Because this runs the services in detached mode, the console remains active in the background. To inspect past output before reconnecting, use:

```bash
docker compose logs --tail=200 rag_console
```

Then, to resume the interactive agent session on the running console container:

```bash
docker compose attach rag_console
```

This sequence lets you review what already happened and then reconnect to the live console session.

## 4. Using the Console Assistant

Once the `rag_console` container is running interactively:
* Enter the session ID when prompted to start or resume a conversation.
* Type your question or prompt directly into the terminal and press **Enter**.
* The system retrieves context from the vector database, formats it through the RAG pipeline, and streams/prints the response generated by `phi3`.
* Session history is automatically tracked and persisted locally inside the `./data/rag/sessions/` directory.
* To exit the console, type `exit` or press `Ctrl + C`.

*(Note: Once historical session data is accumulated, you can generate metrics reports at any time).*

## 5. Analytics & Metrics Reporting

The project includes an automated analytics tool that scans stored chat session logs and computes both quantitative conversation metrics and qualitative impact metrics.

Quantitative metrics include counts of user and AI turns, total messages, total words, and average words per message for both sides. These metrics help quantify conversation length, user engagement, and the verbosity of the assistant.

Qualitative metrics are evaluated through the local LLM and include the inferred main topic of the session, whether the interaction was resolved, and the detected user sentiment. These metrics provide a higher-level view of how effectively the assistant addressed the user query and whether the conversation tone was positive, neutral, or negative.

To run the analytics generator (ensuring `ollama_server` is up):
```bash
docker compose run --rm rag_analytics
```

## 6. Design Patterns

| Pattern | Type | Location | Description & Why It Was Chosen |
| :--- | :--- | :--- | :--- |
| **Singleton** | Creational | `VectorDBClient` | Ensures a single active ChromaDB HTTP client, a shared LangChain `Chroma` wrapper, and a single embeddings model instance. This avoids redundant network connections and repeated model loads across the app. |
| **Factory Method** | Creational | `get_session_history` | Creates or retrieves a persistent `LimitedChatMessageHistory` instance for a given `session_id`, hiding filesystem persistence details from the RAG chain and enforcing a consistent history interface. |
| **Factory Method** | Creational | `load_prompts` | Dynamically resolves prompt templates by version and falls back to a default prompt module, decoupling prompt configuration from chain assembly. |
| **Decorator / Wrapper** | Structural | `RunnableWithMessageHistory` / `LimitedChatMessageHistory` | Wraps the core retrieval chain to persist conversation history and trims context to the last N messages, adding history management without modifying the underlying chain logic. |

## 7. Tech Stack & Justifications

* **Python 3.10+**: Core programming language chosen for its extensive ecosystem in data engineering, machine learning, and AI frameworks.
* **LangChain**: Orchestration framework used to structure prompt templates, chain components, retrievers, and memory management cleanly.
* **ChromaDB**: Selected as the vector database for its fast setup, smooth integration with LangChain, and flexibility to run seamlessly inside containers.
* **Playwright**: Used with Playwright's official Docker images, which come pre-configured with browser binaries and required system dependencies. This enables reliable browser automation for dynamic content ingestion while avoiding low-level dependency and browser install issues.
* **Ollama (`phi3`)**: Local LLM runner ensuring complete data privacy, zero external API costs, and full control over the execution environment during the technical evaluation.
* **Docker & Docker Compose**: Used for containerization to guarantee environment reproducibility across different developer machines.

## 8. Known Limitations & Design Decisions

> ### 🏛️ Data Ingestion Decision
> During the scraping phase, it was identified that primary financial domain targets implement strict WAF (Web Application Firewall) policies blocking automated tools via client-side validation challenges. To fulfill the goals of the technical evaluation without engaging in invasive evasion techniques, and making use of the flexibility granted in the prompt instructions (*"Can be from another bank"*), the ingestion pipeline was oriented toward a more stable alternative financial source. This avoids blocked or unstable scraping targets while keeping the project within non-invasive scraping best practices and preserving the integrity of the use case.

> ### 🗄️ Vector Database Selection
> ChromaDB was chosen for its rapid learning curve and ease of integration. However, it is acknowledged as a known limitation that if the institutional document corpus scales to millions of enterprise-grade records, the architecture would need to migrate to a distributed storage backend like Qdrant or Milvus.

> ### 🧩 Architectural Modularity
> Rather than a single monolithic file, the RAG core logic is structured cleanly within a dedicated `src/rag/engine.py` module handling the conversational chain creation, dynamic prompt versioning, and history management, coupled with `src/run_rag_console.py` as the execution entry point for the interactive console.

> ### 🔒 Context Window & State Management
> Session history is persisted using local JSON files via a customized `LimitedChatMessageHistory` wrapper. This explicitly enforces a maximum message window limit to prevent context window overflow issues and control token consumption when querying local LLM models like `phi3`.

> ### 🔌 Local LLM Constraints
> Relying entirely on a locally hosted Ollama instance guarantees absolute data privacy and eliminates external API dependencies or costs. However, generation speeds and reasoning capabilities are inherently bound by local hardware resources (CPU/GPU capacity allocated to Docker).

## 9. Future Enhancements

* **Web UI Dashboard:** Build a reusable analytics and reporting dashboard or service that can surface retrieval quality, session metrics, and performance trends alongside the chat experience.
* **RAG API Decoupling:** Decouple the RAG workflow into an API service using **FastAPI** or **LangServe**. This keeps the conversational engine separate from client presentation and provides backend endpoints for analytics, dashboards, or other integration clients.
* **Scalable Vector Store:** Evaluate a distributed vector database such as **Qdrant** or **Milvus** for production-scale indexing, faster nearest-neighbor search, and a more scalable storage layer than local Chroma.
* **Context Memory Management:** Improve `LimitedChatMessageHistory` with automated conversation summarization and adaptive retention policies, so older exchanges are compressed rather than discarded when the context window is full.
